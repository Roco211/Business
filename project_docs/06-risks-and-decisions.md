# 06. 风险与关键决策

## 1. 当前默认决策

### D1. 客户端采用 Expo 优先

原因：

- 首版媒体能力和工程效率更重要

回退条件：

- 若端侧模型或厂商 SDK 受限，再切 Bare

### D2. 服务端做统一编排

原因：

- 语音、识图、OCR、确认、审计都需要统一规则

### D3. 语音是主入口

原因：

- 这是最重要的差异化，不应在 MVP 被削弱

### D4. 多模态必须进 MVP

原因：

- 无码商品
- 货架查询
- 纸质进货单

这三类场景决定了纯语音方案不够

## 2. 首版最大风险

### R1. 语音识别准确率不稳定

影响：

- 用户会怀疑整个产品

缓解：

- 结果卡里允许快速修正
- 失败时给文本兜底

### R2. 商品冷启动

影响：

- 无码商品最容易卡住

缓解：

- 拍照建档 + 手工补全 + OCR 抽取并行存在

### R3. OCR 对纸质单据鲁棒性不足

影响：

- 单据辅助价值下降

缓解：

- 先强调“辅助抽字段”，不承诺自动入账

### R4. 微信感 UI 做得像，但流程不像

影响：

- 用户以为会像微信一样顺手，结果操作却很别扭

缓解：

- 保持输入方式简单
- 不要在聊天页塞太多企业后台概念

## 3. 进入试点前仍需拍板的问题

说明：

- 本节问题在**当前施工阶段**都已有默认答案
- 它们不再阻塞工程骨架开工
- 只有在进入真实试点前，才需要重新正式拍板

### Q1. Expo 还是 Bare

建议：

- 当前施工阶段默认：
  - 先 Expo
- 进入试点前再判断是否被厂商 SDK、硬件或端侧模型能力卡住

### Q2. 语音识别基座

建议：

- 当前施工阶段默认：
  - `MockAsrProvider`
- 进入试点前再选一个识别效果最稳的真实供应商，不要同时接多个

### Q3. OCR 与识图供应商

建议：

- 当前施工阶段默认：
  - `MockOcrProvider + MockVisionProvider`
- 进入试点前再选真实 OCR 与识图供应商
- 真实选型优先准确率和速度，不优先最低成本

### Q4. 首版是否必须登录

建议：

- 当前施工阶段默认：
  - `Mock Auth + 单店单老板`
- 如果只是演示版，可继续沿用单店单账号
- 如果准备试点，建议尽早补正式账号和店铺上下文
